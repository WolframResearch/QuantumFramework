# Where the implementation does not match the model

This is the record of the places where the QuantumFramework kernel departs from the model described in `QF-formal-semantics.md`, kept here beside the check scripts rather than inside the shared document. It was first taken against kernel `2d3c29e8` (2026-09-22) and last re-confirmed against the live kernel at `a1799b61` (2026-09-28, paclet `2.1.1`); each item must be re-confirmed against the live kernel before it is relied on, and whether a given item is a genuine defect or a defensible design choice is a separate judgment.

Items fixed since the first audit are not listed. Fixed at the old anchor `56118a44`: a circuit applied directly to a tableau, `qco[ps]`, now returns the resulting `PauliStabilizer`, and a one-qubit measurement operator on a many-qubit tableau now returns the outcome `Association`. Fixed at `fb248528` (the commit "fix six kernel defects and add regression tests", now in `main`; the regression tests it added pass on the live kernel): `QuantumPositiveTransform` on a framework object; the bent trace pair `a != b` on a circuit; a repeated trace wire; `x + qo` on a matrix-type operator; a channel applied to an operator or circuit; and `QuantumEvolve` of a phase-space-picture state with a symbolic, time-independent generator. Fixed at `9933dd18` (its regression test in `Tests/QuantumChannel.wlt` passes on the live kernel): a single-operator Kraus list, `QuantumChannel[{M}]`, which stacked against a dimension-1 environment qudit that collapsed and left the lone output wire on the non-positive environment label, so the object was invalid and could be neither applied nor queried, now routes to the single-operator constructor and is the valid channel rho -> M rho M^dagger. Fixed at `33dd2fc0`: an empty Kraus list, `QuantumChannel[{}]`, which let `{}` reach `MapAt` and leaked `MapAt::partw` before returning a `QuantumChannel` wrapped around a `ConfirmationFailed` failure, now fails at the constructor with a `QuantumChannel::emptyKraus` message and a bare `Failure`, since a channel's operator sum runs over a nonempty Kraus set. Each item below is the call, what it returns now, and the repair. The three that still reproduce:

1. Composition or tensor product across pictures is accepted silently: a Heisenberg operator composed with a Schrödinger one is read in the Schrödinger picture and returned there, with no message. Check the pictures before the fallback. Re-confirmed at `a1799b61`: `h[s]` with `h` an `X` in the Heisenberg picture and `s` a `Z` in the Schrodinger picture returns a Schrodinger `QuantumOperator` of matrix `X.Z = {{0, -1}, {1, 0}}`, silently. Verdict: defensible design choice. The two fast composition rules guard on `qo1["Picture"] === qo2["Picture"]`, so a mismatch skips them and routes through the circuit fallback, which resolves to Schrodinger; the returned matrix is the honest product of the stored matrices and the picture is metadata that never enters the contraction, so no value is wrong, matching QF's shapes-not-physics stance. The one gap is silence: a clean version fires the already-defined but never-used `QuantumOperator::incompatiblePictures` message on the coercion.
2. `QuantumPartialTrace[qo, {{a, b}}]` on an operator whose two wires carry different bases traces the stored coordinates, not the map: a stored identity with a Pauli-X output basis is the Hadamard, whose trace is zero, but the call returns two. Reconcile the bases first, as composition does. Re-confirmed at `a1799b61`: for `QuantumOperator[IdentityMatrix[2], QuantumBasis[QuditBasis["PauliX"], QuditBasis[2]]]` the map is the Hadamard with `Tr = 0`, but `QuantumPartialTrace[qo, {{1, 1}}]` returns `2`, while composition and adjoint reconcile the same mismatched basis (an identity composed onto it keeps the Hadamard, and `SuperDagger[qo][qo]` gives `I`). Verdict: genuine bug. The trace of a map is basis independent, so `0` is the unique right answer and `2 = Tr[stored I]` is a silent wrong number; the model already flags this off-condition as not the trace in section 11. The verified repair folds the local change of basis M = F_in^{-1} F_out into the traced input leg at the state bent-pair vector branch (the qs["StateTensor"] contraction in QuantumPartialTrace.m, reached by the operator path that delegates the trace to the operator's vectorized state), reconciling only the traced wire. Converting the whole operator to the computational basis first is also correct but materializes the dense 2^n by 2^n form, O(4^n) in time and memory (about 29x slower and 137x more memory at 8 qubits for a one-wire trace), whereas the per-wire fold is O(d^2) per pair and leaves the untraced wires and their bases untouched. Confirmed against the whole-operator route across scalar, matrix-valued, bent-pair a != b, non-orthonormal, symbolic, and qutrit cases, and it reduces to the current behavior when the traced wire's two sides already share a basis; the shipped QuantumPartialTrace, QuantumOperator, QuantumChannel, and QuantumMeasurementOperator suites stay green. The state integer-form path, the density bent-pair branch, and the circuit cap/cup path already contract the represented map and need no change (the density branch does leak a TensorContract::lvrank message on a non-computational stored basis, value still correct, a separate cosmetic quirk).
3. `QuantumMeasurementOperator[{E1, E2, ...}]` and its list-of-operators form accept effect matrices without checking that each is Hermitian and positive semidefinite. A non-PSD entry (for instance the nilpotent `{{0,1},{0,0}}`, which has no square root) leaves the matrix square root `MatrixPower[..., 1/2]` unevaluated inside the stored operator; construction emits `TensorRank::rect` three times followed by `General::stop`, yet still returns an object with the head `QuantumMeasurementOperator` carrying that unevaluated square root inside `"Operators"` and `"POVMElements"`. Confirm each entry is Hermitian and positive semidefinite before taking its square root. Re-confirmed at `a1799b61` with a shape change since `fb248528`: the square-root step is `MatrixPower[#, 1/2] & /@ tensor` at `QuantumMeasurementOperator.m:111` for an effect-matrix list and `Sqrt /@ ops` at `:137` for an operator list, neither checked. The single-entry form `QuantumMeasurementOperator[{{{0,1},{0,0}}}]` now leaks `TensorRank::rect` three times and `General::stop` at construction, while the multi-entry form `QuantumMeasurementOperator[{{{0,1},{0,0}}, IdentityMatrix[2]}]` constructs silently but still carries the unevaluated root: its `M1` reads as `{{MatrixPower[{{0,1},{0,0}}, 1/2], 1}, {0,0}}`, `"POVMElements"` carries the same, and applying it returns a `QuantumMeasurement` whose probabilities are `Abs[MatrixPower[...]]^2` rather than numbers; a Hermitian-but-negative effect `{{-1,0},{0,0}}` is accepted too and gives a POVM of `ComplexInfinity` and `Indeterminate`. Verdict: genuine bug. A POVM effect must be Hermitian and positive semidefinite for `Sqrt[E]` to exist, so the object is invalid and the `TensorRank::rect` output is a leaked System message; the repair confirms each effect is Hermitian and positive semidefinite before the root and otherwise fails with a `QuantumMeasurementOperator::` message and a bare `Failure`, as the `QuantumChannel::emptyKraus` fix does. The full design analysis is in `povm-effect-validation-audit.md` (verified live at `923c7035`): the verdict of genuine bug stands, and the repair is made precise in three ways. The guard fires only on fully numeric effects, since a parametric effect list such as `{{{p,0},{0,1-p}}, {{1-p,0},{0,p}}}` builds a correct measurement today and must pass (as `numericStateNotPSDQ` leaves symbolic states alone). The predicate is Hermitian and positive semidefinite together, not positivity alone: `PositiveSemidefiniteMatrixQ[{{1,1},{0,2}}]` returns True because it tests the symmetric part, so a non-Hermitian effect with an existing real square root otherwise sails through to finite but non-POVM numbers. And it checks each effect, not the completeness relation `sum E_m = I`, since a positive-but-non-normalized set is rescaled to unit mean diagonal and stays a valid object. The framing is a domain check on a partial derived construction (`M_m = sqrt(E_m)` is undefined on a non-positive effect), the same category `QuantumChannel::emptyKraus` and the single-operator Kraus reroute already fail cleanly in, not a physics check on an otherwise valid object. The `"POVMQ"` property is no afterward-readout: it is `qmo["Type"] === "POVM"` (`QuantumMeasurementOperator/Properties.m:197`), a structural tag that returns True on the nilpotent, Hermitian-negative, and non-Hermitian inputs alike, unlike a state's genuine `"PhysicalQ"`, which is why a constructor guard fits here where a warn-and-read-later fits the measures.
